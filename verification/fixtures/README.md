# LintCrux (Open Core) — Verification Fixtures

Committed test fixtures consumed by `VERIFICATION_GUIDE.md` and the corresponding integration tests.

## Layout convention

The corpus is the **canned engine output → golden SARIF** model, split per engine into a `generated/<case>/` triple. This mirrors `test/fixtures/` exactly (both trees are regenerated by the same tools).

```
fixtures/
├── engines/
│   ├── verilator/generated/<case>/   # cmdline.txt + output.txt + expected.sarif.json
│   ├── verible/generated/<case>/     #  (case = ansi_color_tty, drift_current, path_with_spaces, …)
│   ├── slang/generated/<case>/
│   ├── ghdl/generated/<case>/
│   ├── svlint/generated/<case>/
│   ├── yosys/generated/<case>/
│   └── helpers/README.md             # engine-corpus regeneration commands
└── stress/                           # large-scale pins (not the corpus itself)
    ├── violations_50k.expected.meta.json   # distribution-meta pin for the in-memory 50K set
    ├── sarif_malformed/                     # truncated / bad_token / wrong_schema rejection cases
    └── helpers/README.md
```

**No `captured/` fixtures are committed today.** The corpus is entirely `generated/`. A `<engine>/captured/<case>/` slot is reserved for real-world engine output rebuilt from public OSS RTL (with a `PROVENANCE.md` + a license drawn from the MIT/BSD/Apache/ISC/CC0 allow-list), but none exist yet — so the `captured_fixture_licenses_test.dart` static guard is **vacuous-by-design** until the first capture lands.

**The 50K/100K stress corpora are not committed as binaries.** They are regenerated deterministically in memory from `test/support/stress_corpus.dart` (byte-stable per seed); only the small distribution-meta pin and the malformed-rejection cases are committed. See `stress/helpers/README.md` for the rationale and the `dart run tool/generate_stress_fixtures.dart` command.

## Adding a new fixture

1. Add the case under `engines/<engine>/generated/<case>/` (never at the unqualified engine root — the static layout guard rejects loose files)
2. Regenerate via `dart run tool/generate_engine_corpus.dart`; commit `cmdline.txt` + `output.txt` + `expected.sarif.json` together in the same commit as the feature it verifies
3. Document any new regenerator command in `engines/helpers/README.md`
4. Reference the fixture from the matching `VERIFICATION_GUIDE.md` section
5. Add the corresponding bullet to `VERIFICATION_CHECKLIST.md`

A shipped feature whose fixtures are missing is a code-review-blocking defect — same rule as WaveCrux.
