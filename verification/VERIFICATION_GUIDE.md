## 3. Foundation

The foundation is infrastructure — most of it is verified by CI going green rather than by hand. The user-visible surfaces (theme, locale, minimum window, file-picker error surfacing) are the manual checks.

### 3.1 What it does (plain language)

The Flutter desktop app boots on Linux / macOS / Windows with the Material-3 theme, five-locale ARB scaffold, `panes`-based IDE layout, keyboard-shortcut infrastructure, the domain model layer (`Violation` / `Severity` / `SourceLocation` / `LintProject` / `SarifReport` …), the in-memory `ViolationStore` with its four indices, and the SARIF read/write round-trip.

### 3.2 Setup

Fresh checkout, `flutter pub get`, Riverpod codegen, `flutter gen-l10n`. Launch `lintcrux` on each target OS.

### 3.3 Step-by-step expected behavior

1. The app launches to the empty-canvas state. No project is required to reach Settings / About / the menu bar.
2. Settings → Appearance: switch light / dark / a preset; the chrome repaints (see §9).
3. Shrink the window: it stops at the 800×500 logical-pixel minimum on every desktop runner.
4. Switch the app locale to zh_CN / ja / ko: all chrome strings render in the chosen locale (no `RenderFlex` overflow).
5. Trigger a file-open with a bogus type filter: the failure surfaces a localized snackbar (`filePickerFailed`), never a silent dead button.
6. **First-run has something to open.** From the empty canvas, **File → Open Project…** → `examples/getting-started/project.lintcrux` opens; **Tools → Run All Engines** (`F5`) reports 7 violations over 6 rules across Verilator and Verible (fewer if only one engine is on `PATH` — the run-status panel names which ran). `examples/vhdl-getting-started/project.lintcrux` reports 3 GHDL warnings. With **no engine installed at all**, **File → Import SARIF report…** → `examples/getting-started/report.sarif` populates the same table, filters and inspector. See `examples/README.md`.

### 3.4 Tier-gate scenarios

Everything in this section is Open Core — no gating. Every surface is free in every edition and both `kBetaPeriod` paths.

## 4. Verilator + Verible + Slang Aggregation

The "good enough to replace reading terminal output" milestone: open a project, run the engines, get one unified filterable/sortable violation table with click-to-source. Slang landed in the same phase alongside Verilator and Verible.

### 4.1 What it does (plain language)

`ParallelEngineRunner` invokes every enabled engine concurrently; each engine's hand-rolled parser normalizes its output into `Violation`s that stream into the store via `replaceFromEngine` as each engine finishes. The violation table virtualizes 50K+ rows, sorts by any column, and filters by severity / engine / rule-substring / file-glob. Selecting a row populates the inspector (rule metadata from the bundled rule database + related locations) and the source-preview pane; double-tap shells out to the configured editor. Inline `// verilator lint_off` pragmas suppress matching violations; per-rule severity overrides and saved filter presets round-trip through the `.lintcrux` project file. Export is SARIF 2.1.0 / JSON / CSV / HTML.

### 4.2 Setup

Use the committed engine corpus under `verification/fixtures/engines/<engine>/generated/<case>/` (canned output → golden SARIF), or point the app at a real Verilog/SystemVerilog project with the engine binaries on PATH. The seeded-lint-run harness (`integration_test/helpers/app_driver.dart`) drives the pipeline with the real parsers and no binaries.

### 4.3 Step-by-step expected behavior

1. Open a `.lintcrux` project (or open source files directly). Run (`F5`). All enabled engines run in parallel; violations appear as each engine finishes.
2. Sort by Severity, then Rule — the header click cycles ascending/descending.
3. Apply a rule-substring filter — the table narrows; combine with a severity chip (AND across dimensions).
4. Select a row with a **plain left-click anywhere in the row body** — severity icon, engine, rule, file, line, or the tooltipped message cell all count. The row highlights **on the same click, with no perceptible delay**; the inspector shows severity + rule id header, message, location, rule metadata (from the rule database), and related locations; the source-preview pane shows ~20 lines around the offending line with it highlighted. Right-click also selects the row before opening the context menu.
   - **Beta-regression guard (2026-07-16):** selection is wired to primary-button *pointer-down*, not `GestureDetector.onTap`. `onTap` cannot fire until the tap recognizer wins the gesture arena, and the row's `onDoubleTap` (open-in-editor) keeps that arena open for the full ~300 ms double-tap window — a single click looked dead, and a second click inside the window was consumed as a double-tap that never selected. If a click ever feels laggy or a double-click leaves the row unhighlighted, this regressed.
5. Double-click a row (or click Open-in-editor) — the row is selected **and** the configured editor launches at the file:line; a bad editor command surfaces a snackbar with the reproducer.
6. Add `// verilator lint_off UNUSEDSIGNAL` above a firing line — the matching violation is suppressed (visible only with the "show waived" chip on).
7. Override a rule's severity — it persists to the `.lintcrux` file and is applied on the next run.
8. Export SARIF / JSON / CSV / HTML — the SARIF validates against the golden shape; the HTML is a self-contained sortable dashboard. With the "show waived" chip on, export SARIF: the pragma-suppressed row's result carries `suppressions: [{kind: inSource, status: accepted, …}]`, and engine-specific fields (e.g. `yosys.severityRaw`) sit in the result's `properties`, not on the result. Import that file back: the row is waived again.

### 4.3.1 Verible against a stock upstream binary (no false clean)

**Why this has its own step.** During the 2026-07-16 shoot, `verible` pointed at
the official `verible-verilog-lint` v0.0-4080 macOS release reported
**"Completed with 0 violations"** on a file the same binary flags 2,365 times.
Three stacked defects: `--lint_output=jsonline` is not an upstream flag (upstream
answers `ERROR: unknown command line flag 'lint_output'` and exits non-zero
having linted nothing); the text-mode parser rejected upstream's column-*range*
syntax `file.sv:8:24-42:`; and upstream writes text-mode diagnostics to **stderr**
while the run path read only stdout. A silent false clean can green-light a dirty
design, so this is verified explicitly on every release.

1. Install a stock upstream `verible-verilog-lint` (any release; nothing in the
   LintCrux distribution bundles Verible) and point Settings → Engines →
   Verible at it, or pass `--verible-path`.
2. Enable only `verible` in the project's `enabledEngineIds` and run against a
   source file you know is dirty (long lines, tabs, unnamed generate blocks).
3. **Expected:** violations appear in the table, with the rule ids upstream
   prints in the trailing bracket (`line-length`, `no-tabs`, …) and the
   messages stripped of their `[Style: …]` category tag. The reported column is
   the range's **start** column.
4. **Expected (invocation):** the engine tries `--lint_output=jsonline` once,
   sees the flag rejection, and **automatically retries in text mode** — no
   `perEngineOptions` / `textModeFallback` hand-configuration required. The user
   sees one completed run; the retry is invisible.
5. **The contract:** an engine run whose binary exits **non-zero** must produce
   either **>0 violations** or an **engine error**, never a clean completed run.
   `verible-verilog-lint` exits 1 *because* it found violations, so exit≠0 alone
   is not a failure — but exit≠0 with nothing parseable is. To exercise this,
   point the engine at a syntactically broken source: the run-status panel shows
   the engine **failed** with the first lines of the binary's output (e.g. the
   `ERROR: unknown command line flag` banner), *not* "Completed, 0 violations".

### 4.4 Edge cases

- A garbage/banner line in engine output is skipped (never fatal) and surfaced as a SARIF `toolExecutionNotifications` entry (see §10).
- A missing engine binary reports the engine unavailable; other engines still run.
- **A non-zero engine exit with no parseable violation is an engine *failure*, not a clean run** (`EngineRunFailedException` → `EngineRunPhase.failed`). This is the guard against the silent-false-clean class; it applies to every engine, not just Verible.

Everything in this section is Open Core — no gating. (The *managed* waiver system, baseline/delta, and trend tracking are Pro; only engine-native pragmas are free here.)

## 5. Yosys Checks + VHDL Foundation

Adds the Yosys check engine (via `crux_yosys`) and the preparatory VHDL scaffolding (GHDL bundled-binary probe + mixed-language project schema) that the GHDL engine builds on.

### 5.1 What it does (plain language)

`YosysCheckEngine` runs a tightly-scoped script (`read_verilog; hierarchy -check -top; proc; check -assert`), feeds Yosys's stderr through `crux_yosys`'s `YosysDiagnosticParser`, and maps each diagnostic into a `Violation` (with a `<module:modname>` synthetic path when file:line is absent). It is registered default-disabled (opt-in per `.lintcrux` `enabledEngineIds`). The GHDL bundled-binary manifest + `GhdlAvailabilityService` land here (no engine yet); `.lintcrux` gains the per-file `ProjectSourceFileLanguage` (`auto`/`verilog`/`systemVerilog`/`vhdl`) schema with extension-based auto-detection.

### 5.2 Setup

Enable `yosys` in a project's `enabledEngineIds`; run against the committed `engines/yosys/generated/` corpus or a real design with Yosys on PATH.

### 5.3 Step-by-step expected behavior

1. Run a project with `yosys` enabled — Yosys `Warning:`/`Error:` lines appear as violations under the right module; a warning with no file:line groups under `<module:modname>`.
2. Confirm `yosys` is off by default in a fresh `.lintcrux` (must be explicitly enabled).
3. Add a `.vhd` source and set its language to `vhdl` (or leave `auto` and rely on the extension) — the schema round-trips through `ProjectFileCodec`; the GHDL engine (§6) is what lints it.
4. Set `Settings > Engines > Yosys check` to **Custom** with a path that does not exist and run — both `yosys` and `cdc` show **Binary not available** (never Completed with 0 violations), and **Probe** reports a probe failure. Point it at a real `yosys` and **Probe** shows that binary's version. The CDC engine has no row of its own: it runs the binary the Yosys check row configures.
5. Headless: `lintcrux project.lintcrux --engine yosys --engine cdc --yosys-path /nonexistent/yosys` exits `3` and the message for each engine names `--yosys-path` (there is no `--cdc-path`); adding `--allow-missing-engines` exits `0` with both listed as skipped.

## 6. Project Files, VHDL, Web Read-Only

Completes the engine roster (GHDL + Svlint), mixed-language routing, `.f` filelist import, custom engine binary paths, per-file incremental re-run, the streaming SARIF parser, and the browser-based read-only viewer.

### 6.1 What it does (plain language)

`GhdlEngine` (`ghdl -a` + `--warn-*`) and `SvlintEngine` (`.svlint.toml` + JSON) join the registry (default-disabled). `EngineLanguageRouter` routes each engine only at the source files whose language it accepts (Verilator never sees `.vhd`; GHDL never sees `.sv`) and surfaces the routing outcome in the run-status panel. `FilelistReader` imports Vivado-style `.f` filelists (`+incdir+`, `+define+`, recursive `-f`, env-var expansion). Custom per-engine binary paths persist in Settings + accept CLI overrides. `runIncremental` re-lints only changed files for engines that support it (Verilator/Slang/Verible), patching the store via `replacePartialFromEngine`. `StreamingSarifReader` ingests very large SARIF documents in bounded memory. The Flutter Web build serves a read-only SARIF viewer (`?sarif=<url>` or file upload) that reuses the desktop dashboard layout — no engine subprocesses, no disk persistence.

### 6.2 Setup

Desktop: open a mixed Verilog+VHDL project with GHDL/Svlint enabled; import a `.f` filelist via `File → Import → Vivado Filelist…`. Web: `flutter build web`, serve `build/web/`, load a SARIF via `?sarif=<url>` or the file picker.

### 6.3 Step-by-step expected behavior

1. Mixed-language project: run — Verilator lints the `.sv`, GHDL lints the `.vhd`; the run-status panel shows each engine's `sourcesUsed`/`sourcesTotal`.
2. `.f` import produces a `.lintcrux` and opens it; `+incdir+`/`+define+`/recursive `-f`/`$ENV` expansion all resolve.
3. Custom binary path: set a per-engine Custom path in Settings → Engines, Probe runs `<binary> --version` and shows the result inline; a CLI `--verilator-path` shadows it for one run. Quit and relaunch with a project tab restored: the Custom path is still selected, and the restored tab's first run already uses it (Tab Diagnostics shows the Custom binary).
4. Incremental re-run: edit one source in an auto-reload project — only the changed engine/files re-lint; other engines' results and the four indices stay correct.
5. Web viewer: load a 100K-violation SARIF by URL — the table renders, filters/sorts responsively, the source-preview pane shows the unreadable-file placeholder (no disk on web), and nothing is uploaded to a server.

### 6.4 Edge cases

- A truncated/malformed SARIF on web is rejected with a typed error, leaving any prior contents intact (see §11).
- A `.f` with a cyclic `-f` include is rejected rather than looping.

### 6.5 Tier-gate scenarios

Open Core — no gating. The web viewer is the free viewing surface; it has no Pro affordances.

## 6.5. Workspace + Multi-Tab + Split-Pane Adoption

LintCrux adopts the cross-suite `crux_workspace` package (extracted from WaveCrux). The single-project Welcome → /viewer flow is replaced by an empty-canvas state + workspace-aware `ViewerScaffold` that hosts `crux.PaneHost`.

The four-pane IDE layout inside each tab (`LintcruxIdeLayout`: rule browser left / violations center / violation details right / run log bottom) is now a thin adapter over the shared `crux_ide_layout` package's `CruxIdeLayout` (suite lift #1) — the per-app `IdeController` + resizer-theme + visibility/size-sync boilerplate is gone, replaced by a `PanelLayoutState → IdePanelLayout(+Sink)` projection. Behavior (defaults, View-menu toggles, drag-to-resize / drag-to-collapse persistence via the settings codec, shared-across-tabs panel state) is unchanged.

### 6.5.2 Multi-tab open

**What:** Opening N `.lintcrux` files yields N tabs in the workspace.

**Setup:** Create two minimal `.lintcrux` project files (e.g. `/tmp/a.lintcrux` and `/tmp/b.lintcrux` referencing one source each).

**Expected:**
- From the empty-canvas state, **Open Project…** → `/tmp/a.lintcrux`. A tab named `a` appears; the project loads; the engines run.
- **File → Open Project…** (or the toolbar action) → `/tmp/b.lintcrux`. A second tab named `b` appears; `b` becomes the active tab; tab `a`'s state survives (the violation table for `a` is not visible but its `ProviderContainer` is alive).
- Clicking the `a` chip switches back instantly — no re-run is triggered, the cursor / filter / sort state is exactly as it was.
- Closing tab `a` via the × button: the violation table for `b` becomes the only visible tab. The empty-canvas state does not return unless tab `b` is also closed.
- Closing the last tab restores the empty-canvas state.

**Edge cases:**
- Opening the same `.lintcrux` path twice yields two distinct tabs (each with its own `LintRunNotifier` instance). The display name is the basename; there is no de-duplication.
- Drag-to-reorder of tab chips works as expected (the `crux_workspace` package provides this).

**Per-tab run-lifecycle scope (seam for the Pro trend dispatcher):** the lint-run *lifecycle bus* (`lintRunLifecycleBusProvider`) is now per-tab — registered in `lintcruxTabOverridesFactory` alongside `violationStoreProvider` and `lintRunProvider` — so each tab's `LintRunNotifier` emits its `running → idle` boundary ticks only to observers scoped to the same tab. This is the seam a per-tab run-completion observer (open-core default: the no-op `LintRunCompletionDispatcher`; Pro overlay: `ProLintRunCompletionDispatcher`, registered per-tab via the new `extraTabOverridesProvider`) reads so it snapshots the *completing tab's own* violation store. The completion *event* bus (`lintRunCompletionEventBusProvider`) stays root, so every tab's completion still aggregates to the one app-wide consumer set (trend store, bookmark stale-detection, Verible auto-run). Open-core users see no behavior change (the open-core dispatcher is a no-op); the seam exists so the Pro trend feature records a data point for the *active* tab's run rather than an empty root store. `ProjectTabContent.build` realizes the per-tab dispatcher (the per-tab analogue of `_EagerStartupGate`).

**Startup-provider liveness (`eagerStartupProvidersProvider` / `perTabStartupProvidersProvider`):** both seams name *providers* to keep alive, and the host holds a real `ProviderContainer.listen` subscription on each — the root container for the eager list (`_EagerStartupGate` in `app.dart`), the tab's own container for the per-tab list (`ProjectTabContent`). This is not a stylistic choice: Riverpod pauses a provider that has no listener of its own, and the pause propagates into any `ref.listen` that provider installed in its constructor. A hook realized with a one-shot `ref.read` is therefore constructed and then immediately stops observing — the registered side effect silently never runs. Open-core ships no hooks in either list, so an open-core user sees no behavior change; the contract exists so overlay-registered listeners (Pro trend ingestion, CXP selection emission, bookmark stale-detection, Verible auto-run) are actually live in a running app rather than only in tests that prop the chain with their own subscription.

**Trend-ingestion failure reporting (`trendIngestDiagnosticsSinkProvider`):** the ingestion listener guards both store resolution and the ingest future, and reports every failure to this seam instead of discarding it. The default sink logs through `package:logging` under `lintcrux.trends`; the listener that reports to it is realized only by the Pro overlay. The Pro overlay overrides the sink to additionally raise a one-time in-app signal, because the Pro SQLite store can genuinely be locked, full, or read-only. A failed ingest never propagates out of the listener callback — the subscription survives, so one bad write drops one run rather than disabling trend tracking for the session.

**Automation status:** per-tab provider isolation — including the per-tab lifecycle-bus isolation and the `extraTabOverridesProvider` open-core default — is covered by test/features/workspace/providers/tab_overrides_factory_test.dart and test/features/workspace/auto_reload_multi_tab_test.dart; the root completion-event bus by test/services/trends/lint_run_completion_event_bus_test.dart. Startup-hook liveness (including the read-vs-listen pause regression) is covered by test/plugins/eager_startup_providers_test.dart and test/plugins/per_tab_startup_providers_test.dart; ingest-failure reporting and subscription survival by test/services/trends/lint_run_completion_listener_provider_test.dart and test/services/trends/trend_ingest_diagnostics_provider_test.dart. The CLI variant (`lintcrux a.lintcrux b.lintcrux c.lintcrux` opening N tabs, one per positional `.lintcrux` project path) is covered end-to-end on a live macOS build by `integration_test/tabs/cli_multi_file_test.dart`. ### 6.5.10 Per-tab scope contract — open flows, dialogs, and root-hosted services

**What:** A tab IS the project scope (ARCHITECTURE.md §10 "Per-tab scope contract"). Three consequences a release must verify:

**Setup:** Open two projects (A with violations, B clean) in two tabs.

**Expected:**

- Tools → App Diagnostics shows the ACTIVE tab's violation count, labelled as the active tab's; the count follows the front tab.
- Settings → Engines → severity overrides edit the ACTIVE tab's project; re-running tab A applies the override, tab B is untouched. The override is written to tab A's `.lintcrux` (only that rule's `severityOverrides` entry changes; relative `rootPath` and sources stay relative): close and reopen the project and the override is still there. Make the file read-only and change an override: an error snackbar names the file.
- Import Vivado filelist opens the generated project as a NEW TAB (same as File → Open), not into an invisible root scope.

**Edge cases:**
- Empty workspace (no tab): the dialogs open against root scope and render their no-project empty states — unchanged behavior.
- Closing the active tab while a wrapped dialog is open: the dialog keeps its captured container until dismissed; reopening resolves the new active tab.

### 6.5.10a Route-mounted dialogs — the leak §6.5.10 cannot see by inspection

**What:** §6.5.10 says dialogs that read per-tab state must mount inside the active tab's scope. This section is the *failure* mode of that rule, because it is silent. A dialog route is a child of the Navigator, and the Navigator sits **above** the per-tab `UncontrolledProviderScope`. So a `showDialog` builder that does not re-bind the container hands the dialog the **root** container, where no project is loaded, the violation store is empty, and the saved-preset list is empty. There is no exception and no log line: the dialog just renders its empty state, and anything it writes lands on a notifier nobody watches.

Fixed 2026-07-21 in `_FilterPresetManageDialog` (violation-table → filter-preset dropdown → **Manage presets…**), found by crux-shared's `route_mounted_scope_leak_test` static guard — the same defect class NetCrux found in beta.

**Setup:** Open a project in a tab. Save at least two filter presets (dropdown → **Save current filters as preset…**).

**Expected:**
1. Open the filter-preset dropdown. The saved presets are listed. Choose **Manage presets…**.
2. The manage dialog lists **the same presets** the dropdown just showed — not "No saved presets yet."
3. Tap the delete icon on one. It disappears from the dialog **and** from the dropdown behind it.
4. **Save current filters as preset…** still works. That dialog is deliberately *not* wrapped: it reads nothing, it returns a name by `pop`, and the caller (still inside the tab scope) performs the per-tab write. A dialog with no reads has nothing to leak.
5. Close the tab and reopen the project: the saved presets (minus the deleted one) are listed again — they are in the project's `.lintcrux` `filterPresets`, with its relative paths untouched. Make the file read-only and save a preset: an error snackbar names the file.

**Edge cases:**
- **Invisible in a single-tab session in the general case** — with one tab, root and tab hold equivalent state for most providers. Filter presets are the exception that made this one visible even single-tab, because nothing ever writes presets at root scope, so the root list is *always* empty. Other members of this class will not be so obvious; two tabs is the reliable reproduction.
- Empty workspace (no tab): `wrapInActiveTabScope` returns the child unchanged and the dialog opens against root — unchanged, correct behaviour.

### 7.2.1 Unreachable-peer indicator (discovered but undialable)

**Setup:** Start LintCrux with the CXP server enabled. Open Tools → Cross-probe Peers. Drop a hand-written manifest into the suite-shared directory whose `host`/`port` point at a port nobody is listening on (e.g. `wavecrux-dead-1.json` with `"port": 1` — reserved/unbindable).

### 7.3 RequestHighlight — rule kind

**What:** A peer sends `request_highlight` with `ElementKind.rule` and the canonical `<engineId>/<ruleId>@<file>:<line>:<column>` path. LintCrux finds the matching violation, clears the filter, and selects the row.

**Setup:** Open a project that produces at least one violation (any of the sample projects works). Note the violation's engine ID, namespaced rule ID, file path, line, and column. Connect a CXP client (the open-core integration test does this in code; for manual verification, use `nc`/`socat` or another Crux app running its own CXP client).

Send (after the standard Hello handshake — see `crux_cxp` README for the wire format):

```json
{
  "cxp_version": "1.0",
  "message_id": "test-1",
  "from": "peer-1",
  "kind": "request_highlight",
  "payload": {
    "element": {
      "kind": "rule",
      "path": "verilator/UNUSEDSIGNAL@/proj/rtl/cpu.sv:42:7"
    }
  }
}
```

**Expected:**
- The matching violation in LintCrux becomes the selected row in the inspector pane.
- Any active filter (severity / engine / rule substring / file glob) clears.
- The peer receives a `request_highlight_ack` with `honored: true` and matching `in_reply_to`.

**Active-tab scoping:** the violation store and table state are per-tab; the root-hosted server resolves the ACTIVE tab's container per request (`ActiveTabContainerHandle`). With two projects open in two tabs, the same `request_highlight` is honored when the tab whose project contains the violation is active, and acks `honored: false` (no matching violation) when the OTHER tab is active — the inbound cross-probe searches what the user is looking at, never a hidden or root-scope store. Selection and filter mutations land in the active tab only.

**Edge cases:**
- Path encoded for a violation that does not exist in the active project → ack with `honored: false`, `reason: "No matching violation in the active project."`. Table state unchanged.
- Malformed path (missing `@`, missing line/column, non-positive numbers) → ack with `honored: false`, `reason: "Malformed rule element path ..."`.
- No tab open at all → same `honored: false` no-match ack (empty-workspace fallback reads the empty root store).

**Coverage:** automated via `test/services/remote/cxp/lintcrux_cxp_request_handler_test.dart` (rule-honored, malformed, no-match) and the rule-kind end-to-end case in `cxp_server_lifecycle_test.dart`; and end-to-end on a live macOS build via `integration_test/remote_control/cxp_inbound_highlight_journey_test.dart` — a real `LocalCxpClient` peer connects over a real socket to the auto-started server, a project is opened through the File → Open seam, and an inbound `request_highlight` is proven to resolve against the **active tab's** per-tab store (row selected + visible), then a second highlight for a violation the tab does not hold acks `honored: false` **without disturbing** the prior selection. The active-tab assertion is not vacuous: rewiring the handler's store thunk to the root container turns the journey red with "No matching violation in the active project."

### 7.6 RequestHighlight — unsupported kinds

**What:** A peer sends `request_highlight` with one of `scope`, `net`, `port`, `marker`, `test`, `breakpoint`. LintCrux cannot represent these.

**Expected:** Ack with `honored: false`, `reason: "LintCrux does not represent <kind> elements."`. Table state and selection unchanged.

**Unknown wire kinds (open enum):** `ElementKind` is open — a peer on a newer protocol revision can name a kind this build does not model. Such a kind decodes to the enum's unknown (`null`) case and is declined exactly like a known-but-unrepresentable kind: a graceful `honored: false` ack naming the wire string, never a throw. An older LintCrux must not be crashable by a newer peer's vocabulary.

**Coverage:** automated via the per-kind loop in `lintcrux_cxp_request_handler_test.dart`.

### 7.6.1 Non-highlight message kinds — matching-type reply (wire-contract)

**What:** A peer sends, as a *directly addressed* message, a kind LintCrux runs no receive-side handler for — e.g. a `notify_selection` sent as a direct address rather than a broadcast (LintCrux's connector announces only `request_highlight` / `request_open_source`, so it never receives `notify_selection` as a broadcast — only a direct address reaches this path). Every inbound request still needs a reply, or the originator times out.

**Expected:** LintCrux replies with an `error_response` carrying `code: "unsupported"`, a human-readable `message` naming the kind (`LintCrux does not handle "<kind>" messages.`), and `in_reply_to` set to the request's `message_id`. Table state and selection are unchanged.

The reply is deliberately an `error_response`, **not** a `request_highlight_ack`. Replying to an arbitrary kind with a `RequestHighlightAck` was a wire-contract violation: the originator correlates the reply on `message_id` but still decodes it by `kind`, so a highlight-ack for a request it never sent is uninterpretable. Only kinds LintCrux actually implements get their matching ack type (`request_highlight` → `request_highlight_ack`, `request_open_source` → `request_open_source_ack`); everything else gets the generic error envelope the v1 protocol defines for exactly this case.

**Edge cases:**
- The `message_id` of the offending message is echoed into `in_reply_to`; a peer awaiting a correlated reply resolves it rather than timing out.
- A malformed *envelope* (undecodable JSON, missing `kind`) is a transport-layer concern handled by `crux_cxp` before dispatch — it yields `error_response` with `code: "malformed_envelope"` / `"unknown_kind"`, not this handler's `"unsupported"`.

**Coverage:** automated via the "NotifySelection … returns an unsupported ErrorResponse, not a fabricated highlight ack" case in `test/services/remote/cxp/lintcrux_cxp_request_handler_test.dart`, which asserts the reply is an `ErrorResponse` (and explicitly `isNot` a `RequestHighlightAck`), carries `CxpErrorCode.unsupported`, echoes a non-empty `in_reply_to`, and leaves table state + selection null.

### 7.7 RequestOpenSource

**What:** A peer sends `request_open_source` with `file_path`, `line`, and optional `column`. LintCrux shells out via the existing click-to-source service (`ClickToSourceService`).

**Send:**

```json
{
  "kind": "request_open_source",
  "payload": {
    "file_path": "/proj/rtl/cpu.sv",
    "line": 42,
    "column": 7
  }
}
```

**Expected:**
- The configured editor command (Settings → Editors) is invoked with the rendered `{file}` / `{line}` / `{column}` argv.
- Ack: `honored: true` when the editor process started; `honored: false` with `reason` when the editor binary cannot be found or the launcher throws.
- `line < 1` is rejected client-side with `honored: false`, `reason: "Invalid line N."`.
- **Containment (CXP §11).** The path must lie inside a directory the user has opened: the directory of every project open in a tab, of every entry in the Recent projects list, and of each source file of the active project (a filelist may name files outside the project tree). With `/proj` open, the example above opens; `"/etc/passwd"` acks `honored: false`, `reason: "file_path is outside the directories open in this session"`, and no editor starts. With nothing open and no recent projects, every path is refused (`"no directory is open in this session"`). A relative or option-shaped path (`"--help"`) is refused as `"file_path must be an absolute path"`. No reason ever repeats the path.
- The same rule applies to `request_open_artifact`: the `.lintcrux` project a peer's `design_id` resolves to in the shared workspace is opened only when it lies inside those directories. A project the user has opened before (it is in Recent projects) opens even when its tab is closed; one the user never opened is refused.
- **Peer auth.** A peer must present, in its `hello`, the token LintCrux published in its discovery manifest; a suite app reads it from the manifest automatically. A hand-rolled peer that omits it is refused `unauthorized` and disconnected before any request is dispatched.

**Coverage:** automated via the open-source unit tests + the end-to-end open-source case in `cxp_server_lifecycle_test.dart` (using a recording launcher). Containment: the "refuses a RequestOpenSource outside the opened projects" and "RequestOpenArtifact opens a recorded project inside the opened projects" cases in `cxp_server_lifecycle_test.dart` (production roots, published through the handle `WorkspaceRoot` fills), the server-level refusal in `lintcrux_cxp_server_test.dart` (refused before `onInbound`), the handler's own check in `lintcrux_cxp_request_handler_test.dart`, and the roots' publication in `workspace_root_test.dart`. ## 10. Robustness — Engine-Output Parsers & Subprocess Orchestration

> Parser robustness and subprocess orchestration. Both are open-core; there is no
> tier gate (the hardening applies to every build).

### 10.1 What it does (plain language)

LintCrux spawns existing lint engines, parses their stderr/JSON into a unified
SARIF model, and aggregates the results. Two subsystems are hardened here:

- **The hand-rolled engine-output parsers** (Verilator, Verible, Slang, GHDL,
  Svlint) now honor an explicit **log-and-continue contract**: any line the
  parser cannot attribute to a violation is *skipped, never fatal*, and is
  surfaced as a SARIF `invocations[].toolExecutionNotifications` entry rather
  than dropped silently. One garbage line never fails the whole run.
- **The NO_COLOR contract**: every engine subprocess is spawned with
  `NO_COLOR=1` and `TERM=dumb` injected, so TTY-detecting engines emit plain
  diagnostics the parsers can read. The spawn layer also decodes engine output
  with `allowMalformed: true` so invalid UTF-8 bytes never crash a run.
- **The subprocess orchestrator** (`ParallelEngineRunner`) gains an
  `EngineWatchdog`: a per-engine wall-clock budget (default 120 s, via
  `engineTimeoutProvider`). A hung engine is killed and reported failed while
  the other engines keep running. Cancellation kills **every** in-flight child,
  not just the awaited one.

### 10.2 Setup

No user setup. The corpus generator regenerates fixtures:

```
dart run tool/generate_engine_corpus.dart   # writes test/ + verification/ trees
```

The committed corpus lives at `test/fixtures/engines/<engine>/generated/<case>/`
(`cmdline.txt` + `output.txt` + `expected.sarif.json`) with a mirror under
`verification/fixtures/engines/`.

### 10.3 Step-by-step expected behavior

1. Run a project whose engine emits a banner line or an unrecognized
   diagnostic → the violation table shows the real violations; the banner does
   **not** appear as a violation and does **not** error the run.
2. Point an engine at a binary that hangs → after the timeout the engine row
   shows a failed/“timed out” state; the other engines’ results still appear;
   no orphaned process remains (verify with `ps`).
3. Cancel a run mid-flight → all spinners stop promptly; no engine subprocess
   survives.
4. Force an engine into colorized output (e.g. a wrapper that ignores
   NO_COLOR) → messages still parse cleanly (the spawn layer suppresses color;
   the parser tolerates residual ANSI in the message as defense in depth).

### 10.4 Diagnostics-assisted verification

The per-engine run log records timed-out / unavailable engines; the SARIF a
run produces carries `toolExecutionNotifications` for every skipped line, so a
reviewer can confirm nothing was silently dropped.

### 10.5 Edge cases

Empty output; a single garbage line; valid + garbage interleaved; multi-line
continuation; path-with-spaces; Unicode filename; residual ANSI; truncated
mid-token JSON; CR/CRLF/lone-LF; NUL bytes / invalid UTF-8; >1 MB line; hung
engine; missing binary; non-zero exit with no parseable output;
stdout/stderr drain (both drained concurrently); cancellation kills all
children.

**Bulk-replacement cost.** `InMemoryViolationStore.replaceFromEngine` runs on
the UI isolate for every re-run *and* every lint-cache hit. Because the
severity / rule / file indices aggregate across engines, removing an engine's
violations one row at a time is quadratic in the widest bucket: a 50K-row
single-severity corpus measured ~49 seconds of frozen UI. Removal is batched
into one linear pass per distinct affected index key, which brings the same
replacement to ~10ms.

The automated guard asserts on `InMemoryViolationStore.lastRemovalScans` — a
deterministic count of the `_all`/index element visits the removal phase
performs (`~4·N` for the batched mono-bucket shape; `~3·N²` for a per-violation
loop) — rather than on wall-clock time. Operation counts are immune to the CPU
contention of the parallel `flutter test` pool (the resolved-AST scope-leak
scanner runs a ~20s analyzer pass in the same pool), so the guard catches a real
quadratic regression by orders of magnitude without ever flaking under load.

**Verify.** Open a project whose run produces tens of thousands of violations in
one severity class, then re-run (`Run → Run All Engines`) and immediately re-run
again so the second pass is a cache hit. The window must stay responsive
throughout — no multi-second beachball between the run starting and the table
repopulating.

> Corpus note: the 50K/100K corpora are generated deterministically in memory

> distribution meta + malformed cases are committed, not a `.zst` corpus
> (avoids multi-MB git blobs and gzip non-determinism while staying
> reproducible).

## 14. Action-surface feedback & destructive-action confirmation

### 14.1 What it does (plain language)

Two contracts that govern what happens when a user activates a menu-bar,
command-palette, or keyboard-shortcut entry.

**Pro-opener feedback.** LintCrux ships every Pro-tier action in the open-core
build's menus and command palette, badged `(PRO)` in the native menu bar and
with a tier chip in the palette, so open-core users can discover what Pro adds
(`kMenuHiddenActions` is deliberately empty). The implementations live in the
Pro overlay behind opener-provider seams. In an open-core build those providers
resolve to `null`, and activation surfaces a localized snackbar rather than
doing nothing — a badged entry that silently no-ops is indistinguishable from a
broken build.

The snack text is chosen from the action's own `requiredTier`, so it can never
contradict the badge the surface rendered: a Pro/Enterprise action says
"<action> requires LintCrux Pro."; an open-core-tier action whose surface has
not shipped yet says the neutral "<action> is not available yet."

**Destructive-action confirmation.** `File → New Workspace` and the
reset-workspace action both close every open tab with no undo. Both route
through a single confirmation dialog before any state is destroyed.

### 14.2 Setup

Run the **open-core** build (`cd lintcrux && flutter run -d macos`). No project
needs to be open.

### 14.3 Step-by-step expected behavior

Pro-opener feedback (open-core build):

1. Open the command palette (`Cmd/Ctrl+Shift+P`). Pro-tier entries — Set
   Baseline, Show Rule Trend Chart, Clear Lint Cache, Review Verible Fixes…,
   Open Waiver Review, Manage Filter Presets, Close All Projects, and the rest
   of the Pro batch — are listed with a tier chip.
2. Activate any one of them. A snackbar appears within ~1 frame reading
   "<that entry's label> requires LintCrux Pro." and dismisses after ~2s.
   Nothing else changes; no dialog, no navigation, no exception.
3. Repeat from the native menu bar. The menu item's label carries the ` (PRO)`
   suffix and produces the same snackbar.
4. Confirm no Pro-badged entry anywhere produces *no* feedback at all.

Destructive-action confirmation:

5. Open two or more project tabs.
6. `File → New Workspace`. A dialog titled "Reset workspace?" appears with the
   body explaining that all open tabs will be closed and that project files on
   disk are untouched.
7. Press **Cancel**. The dialog closes and every tab is still open.
8. Re-run the action and press **Reset**. All tabs close; the app returns to the
   Welcome screen.
9. Repeat both paths for the reset-workspace action (command palette). The
   dialog and both outcomes are identical — the two actions share one

## 15. Update mechanism (`crux_updates`)

**What it does.** LintCrux polls a public version manifest and, when a newer
release exists, shows a dismissible strip above the app content offering
*View Changes* and *Update Now*. There is no in-place download or relaunch —
"Update Now" opens `https://lintcrux.app/download` in the browser.

Three behaviors deserve attention:

- **A failed check never breaks anything.** The check resolves to a typed
  error state; the banner renders nothing on failure, and only the *manual*
  check reports a failure to the user. A user with no network sees no nagging.
- **The auto-check setting gates automatic checks only.** Launch, the 24-hour
  periodic tick, and the on-resume re-check all honour Settings → General →
  *Automatically check for updates*. The Help-menu / palette / About-box
  *Check for Updates* action ignores it and always runs.
- **Every successful fetch records `server_time`** — including a fetch that
  reports the build is already current, and before the newer-version gate.
  That watermark is what hardens beta expiry (§17) against a clock rollback,
  which is why the check still runs on web even though the banner does not.

**Platform scope.** Desktop (Linux / macOS / Windows) shows the banner. The
**web viewer runs the check but never shows the banner** — a web build
self-updates on deploy, so a "download the new version" strip would be noise
that fires between every manifest bump and the corresponding web deploy. There
is no LintCrux mobile build; `checkOnMobile` is left off so a hypothetical
mobile host makes no outbound request at all.

**Setup.** Point the manifest at a local file or a scratch host to drive each
path. The manifest shape (only `version` is required):

```json
{
  "latest": {
    "version": "2.0.0",
    "channel": "stable",
    "release_date": "2026-09-15",
    "changelog_url": "https://lintcrux.app/releases/2.0.0",
    "mandatory": false,
    "min_supported_version": "1.0.0",
    "server_time": "2026-09-15T12:00:00Z"
  }
}
```

**Golden path (update available)**

1. Serve a manifest whose `version` is greater than the running build's.
2. Launch LintCrux. Within a second or two a strip appears above the IDE
   shell reading *"LintCrux 2.0.0 is available."*
3. Click **View Changes** — the browser opens `changelog_url`.
4. Click **Update Now** — the browser opens the LintCrux download page.
5. Click the close (✕) affordance — the strip disappears and the app content
   reflows to full height.

**Dismiss path**

1. With the banner showing, dismiss it. It stays dismissed for the rest of the
   session, including across tab switches and window resizes.
2. Bump the manifest to a *newer* version (2.0.1) and trigger a manual check.
   The banner returns — dismissal is per version, not permanent.

**Mandatory path**

1. Set `"mandatory": true` (or set `min_supported_version` above the running
   version, which forces mandatory even when the flag is absent).
2. Relaunch. The banner shows **no close affordance at all** — it cannot be
   dismissed.

**Manual check — update exists**

1. Help ▸ *Check for Updates* (also in the command palette, and as a button in
   the About box).
2. A transient *"Checking for updates…"* snackbar appears, then the banner.

**Manual check — already current**

1. Serve a manifest whose `version` equals the running build.
2. Run the manual check. The snackbar reads *"You're on the latest version
   (1.0.0)."* and no banner appears.

**Manual check — failure**

1. Point the manifest URL at an unreachable host, or serve a 500.
2. Run the manual check. A single non-fatal *"Couldn't check for updates."*
   snackbar appears. No banner. Nothing else in the app is affected — open a
   project and run engines to confirm.

**Auto-check toggle**

1. Settings ▸ General. *Automatically check for updates* is **on** by default.
2. Turn it off, quit, relaunch. No launch check runs (confirm by watching the
   manifest host's access log, or by serving a newer version and observing no
   banner).
3. With the toggle still off, run Help ▸ *Check for Updates*. The check runs
   and the banner appears — a manual request is always honoured.
4. Relaunch again. The toggle is still off (it is persisted under
   `settings.autoCheckForUpdates`).

**Malformed-manifest soft-fail**

1. Serve `{ this is not json`, then a manifest with no `latest`, then one whose
   `latest` has no `version`.
2. Each case leaves the app silent — no banner, no crash, no error dialog.

**Server-time watermark (feeds §17)**

1. Serve a manifest carrying `"server_time": "2026-09-15T12:00:00Z"` and a
   `version` *equal to* the running build (so no banner appears).
2. Launch, wait for the check, quit.
3. Confirm the value is persisted under the `update.observedServerTime`
   preference key.
4. Relaunch offline. The watermark survives — this is what makes the §17
   clock-rollback defence work on a machine that is later taken offline.

**Edge cases**

- **Web build** — load the web viewer against a manifest offering a newer
  version. No banner ever appears; the fetch still happens (visible in the
  browser network panel).
- **Banner vs. beta-expiry precedence** — with both an available update and an
  expired beta build, the blocking expiry modal covers the update banner.
- **Startup race** — the check that fires before build info resolves reports
  "current" rather than comparing against an unknown version, so a slow
  `package_info` resolution can never produce a spurious banner.

**Tier-gate scenarios**

- `kBetaPeriod = true` (beta): the update mechanism is open to every tier. No
  PRO/ENT badge on the Help-menu entry, the palette row, or the About-box
  button; `LintcruxAction.checkForUpdates.requiredTier` is
  `LicenseTier.openCore`.
- `kBetaPeriod = false` (post-beta): **unchanged**. The update mechanism is
  not a licensed feature and is never gated — an un-updatable build is a
  support burden regardless of what the user paid. Verify by flipping
  `kBetaPeriod` in `crux_license` and confirming the banner, the manual action
  and the toggle all still work under `LicenseTier.openCore`.

## 17. Beta build expiry (`crux_license`)

**What it does.** Each public-beta build carries a shelf life so old betas stop
running and users are pushed onto the current drop. Three states:

- **expiringSoon** — inside the warning window (default 7 days): a dismissible
  strip above the app content reading *"LintCrux Beta expires in N days.
  Download the latest build."*
- **expired** — on or after the expiry date: a blocking, non-dismissable modal
  with *Download latest build* and *Quit LintCrux*. The system back gesture is
  blocked.
- **active / notApplicable** — nothing renders. `notApplicable` covers every
  developer build and every post-beta build.

Distinct from `kBetaPeriod`, which governs feature *gating* and flips once.
This governs one build's shelf life and moves with every beta drop.

**Platform scope.** Desktop only in practice — the release pipeline injects
`BETA_EXPIRY` for desktop builds and deliberately does not for the web viewer,
which self-updates on deploy.

**Setup.** The date is injected per drop, so no source edit is needed:

```bash
# Never expires (the developer default — no define at all).
flutter run -d macos

# Explicitly never expires.
flutter run -d macos --dart-define=BETA_EXPIRY=0

# Expiring soon: pick a date 3 days out.
flutter run -d macos --dart-define=BETA_EXPIRY=<yyyymmdd 3 days from today>

# Already expired: pick yesterday.
flutter run -d macos --dart-define=BETA_EXPIRY=<yyyymmdd yesterday>

# Narrow the warning window to prove it is configurable.
flutter run -d macos --dart-define=BETA_EXPIRY=<+3 days> \
                     --dart-define=BETA_EXPIRY_WARNING_DAYS=2
```

**Active path**

1. Launch with no `BETA_EXPIRY`, or with a date far in the future.
2. No banner, no modal. The app is exactly as it was.

**Expiring-soon path**

1. Launch with an expiry 3 days out.
2. A strip appears above the IDE shell with the day count. The plural is
   correct for 1 day as well as N days — check both.
3. Click **Download** — the browser opens the LintCrux download page (the same
   page the update banner uses).
4. Click the ✕ — the strip disappears for the session.
5. Suspend and resume the app. The strip **returns** — a dismissal lasts the
   session, and a returning user is reminded again.

**Expired path**

1. Launch with yesterday's date.
2. A blocking modal covers the app. The content behind it is visible but not
   interactive — try clicking a violation row and confirm nothing happens.
3. The system back gesture / Escape does not dismiss it.
4. Click **Download latest build** — the browser opens the download page.
5. Click **Quit LintCrux** — the process exits. **This step matters most on
   Windows and Linux**, where the window close button sits behind the modal
   barrier; without the quit button the modal would be a dead end.

**Clock-tampering path (the §15 pairing)**

1. Launch a build whose expiry is a week out, with the manifest serving a
   `server_time` **past** that expiry date. Let the update check run, then quit.
2. Set the device clock back a month.
3. Relaunch, offline. The build is still treated as **expired** — the trusted
   clock is the later of the device clock and the persisted watermark.
4. Control: wipe the `update.observedServerTime` preference, keep the clock
   rolled back, relaunch. Now the build reads as active — with no observed
   server time the device clock is all there is, which is the accepted
   fresh-install / never-online behaviour.

**`kBetaPeriod = false` no-op path**

1. Flip `kBetaPeriod` to `false` in `crux_license` and launch with any
   `BETA_EXPIRY` value at all.
2. Nothing renders. `kBetaExpiry` resolves to `null` for a production build, so
   a shipped release can never expire.

**Edge cases**

- **Banner has no Overlay ancestor.** The strip renders above the app's
  Navigator, so it deliberately carries **no `Tooltip`** — a Tooltip there
  throws "No Overlay widget found" and red-screens every launch in the warning
  window. The accessible name is a `Semantics` label instead.
- **Boundary day.** A build with `BETA_EXPIRY=20260901` is expiringSoon through
  2026-08-31 and **expired** at the start of 2026-09-01 — expiry is reckoned in
  whole calendar days, independent of time of day.
- **Invalid dates.** `20261301`, `20260230`, `-5` and `19990101` all resolve to
  "never expires" rather than to a crash or an immediate block.
- **Mid-session.** The status is read at startup and on resume only, never
  mid-session — a build never expires out from under work in progress.

**Tier-gate scenarios**

- `kBetaPeriod = true` (beta): expiry applies to **every tier**. A Pro or
  Enterprise licensee is blocked by an expired beta build exactly as an
  open-core user is — this is build shelf life, not a licence check. Verify by
  overriding `licenseTierProvider` to `pro` / `enterprise` and relaunching an
  expired build.
- `kBetaPeriod = false` (post-beta): the mechanism is inert for every tier —
  `kBetaExpiry` is `null` regardless of the injected define.

## 19. Headless CI binary (`bin/lintcrux.dart`)

### 19.1 What it does (plain language)

The desktop app always creates a window, so it can never be the thing a
CI job runs. `bin/lintcrux.dart` is a **second executable** built from
the same open-core package: it loads a project (or a list of loose HDL
files), runs the enabled engines, applies severity overrides and source
pragmas, optionally compares the result against a baseline, writes an
export, and exits with a code a pipeline can branch on. No window, no
Flutter, no display server.

Why it exists in this shape rather than as a `--headless` flag on the
app: a Flutter desktop binary creates its window during engine
initialization, before any Dart argument parsing runs. A flag cannot
suppress that. A separate executable is also the shape every CI user
already expects (`verible-verilog-lint`, `verilator`, `slang` are all
plain binaries).

**The exit-code contract is the feature.** `verible-verilog-lint` exits
`1` *because it found violations*, which makes "non-zero" carry no
information at all. LintCrux's codes are disjoint so a job can tell
"your RTL has findings" from "the linter did not work":

| Code | Label | Meaning |
|---|---|---|
| `0` | `clean` | Nothing to report, **or** findings present with no gate requested. A bare `lintcrux project.lintcrux` is a reporting command, not a gate. |
| `1` | `violations` | `--exit-code` was passed and ≥1 non-suppressed violation remains. |
| `2` | `new-violations` | `--fail-on-new-violations` was passed and ≥1 violation is absent from the baseline. |
| `3` | `run-failed` | An engine failed / timed out / was unavailable, the project could not be loaded, the `--config` overlay was malformed, the baseline was corrupt, or the export could not be written. **The violation count printed alongside this code is a partial result.** |
| `64` | `usage-error` | Bad flag, `--export` without `--out`, unknown `--engine` id, a positional that is neither a `.lintcrux` nor a lintable source file, or a path that does not exist. Same value the GUI front door has always returned for a parse error (`EX_USAGE`). |
| `65` | `data-error` | `--import-filelist` could not read or convert the `.f`, or `--import-edam` could not read or convert the `.eda.yml`. Same value as the GUI (`EX_DATAERR`). |

Escalation order: run failure outranks everything (a count from a broken
run is untrustworthy), then `--fail-on-new-violations` (2), then
`--exit-code` (1). Passing both gates therefore reports `2` on a
regression and `1` on pre-existing debt — the distinction a reviewer
actually wants.

Two behaviors are deliberately strict, both instances of the same
"silent false clean" defect class that `EngineRunFailedException`
closes on the engine side:

- **An unusable positional is an error, not a skip.** Before this
  binary existed, a non-`.lintcrux` positional was silently dropped, so
  `lintcrux typo.sv` reported a clean run over zero files.
- **A missing engine binary fails the run by default.** A job that asked
  for Verilator and silently ran zero engines is a green build that
  means nothing. `--allow-missing-engines` opts out explicitly.

### 19.2 Setup

Build the binary (`dart compile exe` refuses to run while any package in
the resolution declares a native build hook — `objective_c`, pulled in
transitively by `path_provider_foundation`, does; `dart build cli` is
the supported replacement):

```bash
tool/build_cli.sh                     # → build/cli/bundle/bin/lintcrux
build/cli/bundle/bin/lintcrux --help
```

The emitted executable runs standalone — nothing else from the bundle is
needed for the open-core binary. (The **Pro** binary is different; see
the Pro guide.)

Fixtures: `test/fixtures/projects/basic_warnings/` and
`test/fixtures/projects/clean_project/`. At least one engine must be on
`PATH`; Verilator is the least friction (`brew install verilator`,
`apt install verilator`).

### 19.3 Step-by-step expected behavior

Run each from the repo root with `echo $?` after it. **Assert on the
shell's exit status, not on the printed summary** — the summary is a
convenience, the code is the contract.

1. **Reporting run.** `lintcrux test/fixtures/projects/basic_warnings/project.lintcrux`
   Expected: one `file:line:col: severity: [rule] message` line per
   violation, then a summary line ending `[exit 0: clean]`. Exit `0`
   even though violations were reported — no gate was requested.
2. **`--exit-code`.** Same invocation `--exit-code`. Expected: identical
   output, summary ends `[exit 1: violations]`, exit `1`.
3. **Clean project.** `lintcrux test/fixtures/projects/clean_project/project.lintcrux --engine verilator --exit-code`
   Expected: `no violations`, exit `0`.
4. **Missing engine is a failure.** Drop the `--engine verilator` from
   step 3 on a machine without Verible. Expected: stderr names the
   engine, the reason, and every escape hatch
   (`--verible-path`, `--engine`, `--allow-missing-engines`); exit `3`.
5. **Missing engine tolerated.** Add `--allow-missing-engines`.
   Expected: the same message demoted to `lintcrux: note:` with
   `(skipped: --allow-missing-engines)`; exit `0`.
6. **Unusable positional.** `lintcrux notes.txt`. Expected: stderr names
   the file and lists the accepted extensions; **stdout is empty** (no
   `no violations` line, which would read as a clean result); exit `64`.
7. **Unknown engine.** `--engine verlator`. Expected: stderr lists the
   registered engine ids; exit `64`.
8. **`--export` without `--out`.** Expected: usage error naming `--out`;
   exit `64`. A CI step that meant to produce an upload artifact and
   produced nothing must fail loudly.
9. **SARIF export.**
   `lintcrux <project> --export sarif --out lint.sarif`. Expected: the
   file lands, the summary reports `— wrote lint.sarif`, and the
   document has:
   - `version: "2.1.0"` and a `$schema` naming sarif-2.1.0;
   - one `runs[]` entry per engine, `tool.driver.name` = engine id;
   - `automationDetails.id` = `<project-name>/<engine-id>` with **no
     timestamp** (GitHub groups uploads into a category by this id; a
     timestamp would make every upload a new category instead of
     superseding the last);
   - `originalUriBaseIds["%SRCROOT%"].uri` = a `file:///…/` URI for the
     project root;
   - every `artifactLocation` = `{uri: <repo-relative>, uriBaseId: "%SRCROOT%"}`.
     **An absolute `uri` here is the defect to watch for** — GitHub
     accepts the upload and then annotates nothing, because no file in
     the checkout matches `/Users/someone/work/rtl/top.sv`.
10. **Other formats.** `--export json|csv|html --out …`. Expected: each
    writes; `csv` starts `severity,engine,rule,…`; `html` is a
    self-contained table.
11. **`--config` overlay.** Write `{"severityOverrides":{"verilator/WIDTHTRUNC":"note"}}`
    and pass `--config`. Expected: the violation prints as `note:`.
12. **Malformed `--config`.** Add an unknown key. Expected: stderr names
    the bad key and lists the overlayable keys; exit `3`. A CI job whose
    overrides silently did not apply reports the wrong answer.
13. **Ad-hoc sources + `--top`.**
    `lintcrux rtl/top.sv rtl/other.sv --top top_module --engine verilator`
    Expected: lints without a project file; the synthetic project is
    rooted at the sources' common ancestor.
14. **`--fail-on-new-violations`, both directions.** This needs a
    baseline, which LintCrux **Pro** writes — see the Pro guide's
    `baseline set` section. With a baseline in place:
    - unchanged tree → `0 new, N pre-existing`, exit `0`;
    - introduce a violation → the new line is annotated `(new)`, the
      summary reads `1 new`, exit `2`;
    - revert → back to exit `0`;
    - both gates passed on a regression → exit `2` (the specific code
      wins over `1`);
    - **no baseline file at all** → every violation is new, exit `2`,
      with a `lintcrux: note:` explaining where the file was looked for.
      Strict, not broken;
    - **copy the project (baseline included) to a different directory**
      and run there → still `0 new`, exit `0`: fingerprints are
      project-relative, so a baseline set on a desktop gates a CI checkout;
    - **a version 1 baseline** (written by an earlier build) → read,
      migrated, and it gates exactly as before.
15. **Corrupt baseline.** Truncate `.lintcrux-baseline.json`. Expected:
    exit `3`, not a silent pass. A gate that cannot read its baseline
    must not wave the build through.
16. **`--import-filelist`.** Expected: prints `Imported filelist → …`,
    writes the `.lintcrux`, then lints it. A broken `.f` exits `65`.
16a. **`--import-edam`.** Expected: prints any `lintcrux: warning:`
    advisories to stderr, prints `Imported EDAM → …`, writes the
    `.lintcrux`, then lints it. A broken / missing `.eda.yml`, or one
    with zero lintable HDL sources, exits `65`. Full flow in §22.
17. **Pragma waivers.** A violation inside a
    `// verilator lint_off RULE` / `lint_on` range. Expected: not listed,
    counted as `N suppressed` in the summary, does not trip `--exit-code`.
18. **`--quiet`.** Expected: the per-violation listing disappears, the
    summary line and the exit code are unchanged.

### 19.4 Diagnostics-assisted verification

- `--help` prints the full flag table *and* the exit-code table. If a
  flag exists and is missing from `--help`, `test/core/cli/lintcrux_cli_test.dart`
  fails.
- Every summary line ends `[exit <n>: <label>]`, so a CI log is
  self-documenting without the reader consulting this guide.
- stderr uses two distinct prefixes: `lintcrux: note:` (non-fatal) and
  `lintcrux: error:` (fatal). Only the latter implies a non-zero code.
- Language routing is visible: an engine that received zero compatible
  source files is reported as a `note`, not silently dropped.

### 19.5 Edge cases

| Case | Expected |
|---|---|
| Relative `rootPath` in a committed `.lintcrux` | Ignored in favor of the project file's own directory. Committed files carry a repo-root-relative `rootPath` naming their own directory; joining it would double the path and silently defeat SARIF relativization. |
| Absolute `rootPath` | Honored as written. |

### 19.6 Tier-gate scenarios

The headless binary is **entirely open core**. Every flag in §19.3
works in a free build, under both `kBetaPeriod = true` and
`kBetaPeriod = false`; there is no tier check anywhere in
`HeadlessRunner`, and `lintcrux --help` carries no `(PRO)` suffix.

The one tier-adjacent seam is the baseline: `--fail-on-new-violations`
**reads** `.lintcrux-baseline.json`, and only LintCrux Pro **writes**
one. An open-core user who runs the gate with no baseline gets the
strict reading (everything new, exit `2`) plus a note explaining where
the file was sought — a working gate, not a broken one. Verify both:

- **Open-core build, no baseline** → exit `2` + the note. Never exit `0`.
- **Open-core build, Pro-written baseline present** → the gate honors it
  fully. Reading a baseline is not gated.

## 20. Workspace launch behavior — tab dedupe, restore gate, persisted state

Fixes three symptoms reported during the beta. Two of them are
`crux_workspace` seams LintCrux now opts into; the third is a
documentation gap that made the other two impossible to diagnose.

### 20.1 What it does (plain language)

**(a) Tab dedupe.** Opening a project LintCrux already has open now
*focuses* that tab instead of adding a second one. Before, every launch
that carried a `.lintcrux` path on the command line appended one more tab
for the same project — unbounded, one per relaunch (seven identical
`riscv-soc` tabs were observed in the field), because the restored
workspace held the absolute path the document was saved with while the
shell handed over whatever spelling the user typed.

Identity is a *canonical path key* (`canonicalPathKey` from
`crux_io`), not the raw string: absolute, `..`-collapsed,
trailing-separator-stripped, symlink-resolved (`/tmp` → `/private/tmp` on
macOS), and case-folded on macOS/Windows. `LintcruxWorkspaceCodec.identityOf`
returns it; `WorkspaceNotifier.openTab(dedupe: true)` consults it. The
empty-canvas tab has no identity, so two blank tabs still open.

The same keys now drive `ProjectWorkspaceSync`, which used to key its
tab↔registry map on the unprocessed path string. The registry stores
`p.normalize(p.absolute(path))`, the tab stores what it was given, and
those two disagreeing made the sync re-record the same project on every
convergence pass and open a second tab under the registry's own spelling.

**(b) Restore gate.** `Settings → General → Restore tabs on launch` now
actually works. `bootstrap` resolves the persisted preference once, before
`runApp`, and `LintcruxWorkspaceNotifier.shouldRestoreOnLaunch` reads that
decision *before* the workspace document is loaded; declining starts from an
empty workspace and **leaves the document on disk**, so turning the setting
back on restores the session that was there. Before this, the preference
existed in the settings model, was never read by anything, and had no UI at
all — the reporter set it with `defaults write` and nothing happened.

The preference lives under `settings.restoreTabsOnLaunch`, the key
`CoreSettingsCodec` owns suite-wide, so an existing hand-set value is the one
that takes effect — a product-scoped key would have made the bug look fixed
while the reporter's setting stayed dead. The gate reads a plain `bool`
resolved at bootstrap rather than awaiting storage: `SharedPreferences`
replies on the real event loop, and awaiting that on the launch path hangs
every workspace-touching widget test under fake-async (they time out rather
than fail).

The gate also suppresses the *registry* re-seed at launch (see (c)):
`ProjectWorkspaceSync`'s registry-originated activation step will not open a
tab while the launch restore was declined and no tab exists yet. Otherwise
the tabs come back through the side door on the very launch the user asked
for a clean start.

**(c) Where the state actually lives.** Two different `workspace.json`
files exist per install, and deleting the wrong one explains "I deleted
`workspace.json` and the tabs still came back":

| Path | Owner | Holds |
|---|---|---|
| `<appSupport>/workspace.json` | `crux_workspace` `WorkspaceService` | **tabs + panes** — the one that controls what you see |
| `<appSupport>/lintcrux/workspace.json` | `crux_projects` `JsonFileProjectRegistry` (Pro) | open / active / recent **projects** |
| `<appSupport>/sessions/<tabId>.lintcrux-session` | per-tab sidecars | survives `clear()`; deleted per-tab |

On macOS `<appSupport>` is
`~/Library/Application Support/com.ferriteengineering.lintcruxPro/`
(open-core builds: `com.ferriteengineering.lintcrux/`). The two files
re-seed each other: `OpenProjectInWorkspace.openProject` opens a tab **and**
`ProjectWorkspaceSync` records it into the registry, so a CLI open feeds
tomorrow's re-seed. Clearing state means clearing **both**.

### 20.2 Setup

- A real `.lintcrux` project on disk. `verification/fixtures/` has several;
  `riscv-soc.lintcrux` from the scenario corpus matches the bug report.
- Quit LintCrux before editing anything under `<appSupport>` — the workspace
  document is flushed on exit and will overwrite your edit.
- To inspect the preference:
  `defaults read com.ferriteengineering.lintcruxPro flutter.settings.restoreTabsOnLaunch`
  (`SharedPreferences` namespaces its keys under `flutter.`).

### 20.3 Step-by-step expected behavior

**Dedupe — CLI**

1. Launch LintCrux, open `riscv-soc.lintcrux`, quit. One tab is persisted.
2. Relaunch with the project as a positional argument:
   `lintcrux /abs/path/riscv-soc.lintcrux`.
   → Exactly **one** tab. The restored tab is focused; no second tab appears.
3. Repeat step 2 five more times. → Still exactly one tab. (This is the
   regression: it used to be one more tab per launch.)
4. Relaunch from the project's own directory with a *relative* argument:
   `lintcrux ./riscv-soc.lintcrux`. → Still one tab.
5. Relaunch with a `..`-bearing spelling
   (`lintcrux sub/../riscv-soc.lintcrux`) and, on macOS, a `/tmp/...` copy
   whose real path is `/private/tmp/...`. → Still one tab in each case.

**Dedupe — in-app**

6. File → Open, pick the project that is already open.
   → The existing tab is focused. No second tab, and — important — the
   focused tab's filters, sort, selection and current run are **unchanged**
   (a dedupe focuses, it does not re-run).
7. Open a *different* project. → A second tab, as always.
8. Open two empty-canvas tabs. → Both stay; blank tabs never fold together.

**Restore gate**

9. With two projects open, quit. Relaunch. → Both tabs return (default is on).
10. Settings → General → turn **Restore tabs on launch** off. Quit. Relaunch.
    → Empty workspace, no tabs. Nothing on disk was deleted.
11. Settings → General → turn it back on. Quit. Relaunch.
    → Both tabs from step 9 return, with their filter/sort state.
12. With the setting off, relaunch **with** a positional `.lintcrux`
    argument. → Exactly one tab: the CLI one. Nothing else is restored.
13. With the setting **on**, relaunch with a positional argument naming a
    project that was already in the restored session. → The restored tabs,
    plus **exactly one** tab for the CLI project — the restored one,
    focused. Not a duplicate.

**Persisted state / stale tabs**

14. Note a tab from an old session you no longer want (the report had a
    stale `clean_project` tab). Close it in the app, then quit.
    → It is gone from `<appSupport>/workspace.json` **and** from
    `<appSupport>/lintcrux/workspace.json`'s `open_projects` (it moves to
    `recent_projects`).
15. Full manual reset: quit, delete **both** files above (and the
    `sessions/` directory if present), relaunch. → Empty workspace, empty
    project switcher, empty recents. Deleting only one of the two leaves
    the other to re-seed.

**Command palette Enter** (fixed by the same `crux-shared` bump)

16. Open the command palette, type enough of an action's name to highlight
    it, press **Enter**. → The action runs. Previously nothing happened and
    only a mouse click worked. Also check ↑/↓ moves the highlight without
    moving the text caret, and Escape closes the palette once (not popping
    the route behind it too).

### 20.4 Diagnostics-assisted verification

With diagnostics available (always in a debug build; in a release build,
Settings → General → Enable diagnostics), the Tab Diagnostics drawer shows
the active tab's project path. Two tabs for one project are unmistakable
there; so is a tab whose path spelling differs from the registry's.

`defaults read com.ferriteengineering.lintcruxPro | grep restoreTabs` shows
the persisted preference, which must agree with the Settings switch.

### 20.5 Edge cases

- **Project file deleted between sessions.** The restored tab keeps its
  path; identity is still computable (symlink resolution fails soft and
  falls back to the normalized absolute path), so a CLI open of the same
  now-missing path still dedupes rather than stacking.
- **Two case-different spellings on a case-sensitive Linux volume.** These
  are genuinely two files and get two tabs. On macOS/Windows they are one
  file and get one tab. This is deliberate; `filesystemIsCaseInsensitive`
  is a platform heuristic, not a per-volume probe.
- **Deliberate second view.** `openTab(dedupe: false)` still opens a second
  tab for one project. Nothing in the UI does this today; it exists for a
  future side-by-side compare.
- **Unreadable preference.** If the settings store throws (no platform
  channel, plugin not registered), the launch **restores**. Losing a session
  because a preference was unreadable is the worse failure.
- **Toggle flipped during launch.** Turning the switch off in the first
  frames is not overwritten by the value that was on disk at start-up.
- **Restore off + user opens a project.** Normal behavior resumes
  immediately: the tab records into the registry and the switcher works.

### 20.6 Tier-gate scenarios

Everything here is open-core, on every tier, under both `kBetaPeriod`
values. There is no `(PRO)` suffix on the Settings row and no tier badge.

The one tier-visible interaction is the registry: open-core runs
`NoopProjectRegistry` (single-project, nothing persisted), so
`<appSupport>/lintcrux/workspace.json` only exists in a Pro build. Step 15's
"delete both files" reduces to one file in an open-core build — verify the
open-core build restores nothing after deleting
`<appSupport>/workspace.json` alone.

## 21. Verible rule profiles — the lowRISC / OpenTitan style guide

### 21.1 What it does (plain language)

A **rule profile** is a named, curated selection of `verible-verilog-lint`
rules that LintCrux passes to the engine, so a project can say "check me
against the lowRISC / OpenTitan Verilog style guide" without anybody
hand-transcribing 41 rule names and three configuration values into a
config file.

One profile ships: `lowrisc`. It encodes the lowRISC Verilog Coding Style
Guide as enforced by OpenTitan's own
`hw/lint/tools/veriblelint/lowrisc-styleguide.rules.verible_lint` — the
guide Ibex, OpenTitan and much of the RISC-V world already follow. The
upstream revisions it was transcribed from are cited in
`lib/services/engines/verible/builtin_rule_profiles.dart`; refreshing the
profile means diffing against those two SHAs.

Two things it deliberately is **not**:

- It is **not** a `FilterPreset` / "Filter preset" dropdown entry. Those
  filter the violation table *after* a run. A style-guide profile has to
  change what the engine is asked to check, so it rides the engine
  invocation instead (`perEngineOptions` → `LintRunRequest.options` →
  command line), next to `rulesConfigSearch` and `textModeFallback`.
- It is **not** a Pro feature. Curated convenience ships open core on
  every tier.

Upstream expresses the profile as a delta on `--ruleset=default`, which
means what "the lowRISC profile" checks would silently change whenever
Verible promotes or demotes a rule in its own default set. LintCrux
resolves that delta once, at a verified Verible version, and ships the
resulting closed set with `--ruleset=none` — so the profile is
reproducible under the name it carries.

### 21.2 Setup

1. A `verible-verilog-lint` on `PATH` (or bundled / custom-configured).
   The shipped rule names were verified against **v0.0-3795-gf4d72375**
   (the release pinned in `tool/bundled_engines.yaml`) and
   **v0.0-4084-gf3e4d98b**; both expose the same 42-rule default set.
2. A `project.lintcrux` with Verible enabled and at least one
   SystemVerilog source.
3. Add the profile to the project file:

   ```json
   "perEngineOptions": {
     "verible": { "ruleProfile": "lowrisc" }
   }
   ```

   Headless / CI runs can inject the same key through the
   `--config-overlay` allowlist (`perEngineOptions` is overlayable) —
   which is where style-guide enforcement usually lives.

### 21.3 Step-by-step expected behavior

1. Run the lint. Verible is invoked with `--ruleset=none` followed by a
   single comma-separated `--rules=…` carrying 41 tokens. Confirm from
   Diagnostics → the engine's command line, or by running the same
   arguments by hand.
2. The run **completes** — no `EngineRunFailedException`, no
   "exited N without producing a parseable violation". That is the whole
   correctness claim: a profile naming a rule the binary does not have
   makes Verible exit non-zero having linted nothing.
3. Lint a file with a lower-case `parameter` name (e.g.
   `parameter int bad_param_name = 1`). It is flagged by
   `parameter-name-style`, whose message quotes the CamelCase-or-ALL_CAPS
   regex — that is upstream's `localparam_style:CamelCase|ALL_CAPS`
   configuration arriving intact, not Verible's default.
4. Lint a file with a **nested struct typedef**. It is *not* flagged:
   `typedef-structs-unions` is absent from the profile because the
   lowRISC guide permits nested struct definitions. Re-run without the
   profile and the same file is flagged — that difference is the profile
   doing its job.
5. A line longer than 100 columns is flagged by `line-length`.
6. Every violation the profile produces resolves in the Inspector to a
   rule with a help URL and tags — i.e. the profile's rule names and the
   bundled rule database (`lib/data/rules/verible.json`) agree.

### 21.4 Edge cases

- **Typo'd profile id** (`"ruleProfile": "lowrsic"`): the engine fails
  loudly with `unknown Verible rule profile "lowrsic" (known: lowrisc)`
  in the diagnostics panel, and the subprocess is never spawned. It must
  never fall back to Verible's defaults — a run under a rule set nobody
  chose is the same false-confidence failure as a silent false-clean.
- **Non-string value** (`"ruleProfile": true`): same failure shape.
- **Absent / omitted key**: no `--rules` and no `--ruleset` appear at
  all; Verible runs its own defaults, exactly as before this feature.
- **Profile + `.rules.verible_lint`**: both are passed. The profile is a
  starting point, not a lock; the project's own config file still
  applies on top when `rulesConfigSearch` is on (or the file sits in the
  project root).
- **Profile + `extraArgs`**: the profile's flags are emitted *before*
  `EngineBinaryConfig.extraArgs`, so a power user who puts
  `--ruleset=all` in `extraArgs` still wins.
- **Older Verible**: the profile is valid across v0.0-3795 … v0.0-4084.
  On a build older than the verified floor an unknown rule name would
  make the run fail — visibly, in diagnostics, which is the intended
  behavior.

### 21.5 Tier-gate scenarios

- Open core, EDU, Pro, Enterprise, and both `kBetaPeriod` values: the
  profile is available and behaves identically. There is no FeatureGate,
  no `(PRO)` affordance, and no Pro override involved.

## 22. FuseSoC EDAM import (`--import-edam` / `File → Import FuseSoC EDAM…`)

### 22.1 What it does (plain language)

Imports a FuseSoC/Edalize **EDAM** file (`.eda.yml`) — the fully
resolved project description FuseSoC generates in its build directory —
into a `.lintcrux` project. EDAM is CAPI2 *after* every hard problem has
been solved: conditionals evaluated, the dependency closure staged on
disk, `toplevel` a plain string. `EdamReader` maps `files[]` (sources +
per-file `file_type` language + `is_include_file` directories),
`toplevel`, `vlogdefine` parameter defaults, `tool_options.verilator`
(`-W*` → `warnFlags`, the rest → `extraOptions`), and `file_type: vlt`
Verilator waivers (→ the Verilator engine's `waiverFiles` option, **not**
the shared source list). Per-file core provenance (`files[].core`) is
recorded in the project's `sourceFileProvenance`. Unsupported constructs
(hooks, filters, vpi, other tools' options, plusargs) warn and continue;
only an unreadable/unparsable file or zero lintable sources fails the
import. This is the first step of the EDAM integration agreed with the
FuseSoC maintainer.

### 22.2 Setup

```bash
pip install fusesoc
fusesoc library add serv /path/to/serv
fusesoc run --target=lint --setup award-winning:serv:servant
# → build/award-winning_serv_servant_1.4.0/lint/*.eda.yml
```

Or use the committed captures under `verification/fixtures/edam/`.

### 22.3 Step-by-step expected behavior

1. CLI: `lintcrux --import-edam <path>.eda.yml --sarif out.sarif`
   prints `Imported EDAM → …`, writes the `.lintcrux` beside the EDAM
   (double extension stripped: `design.eda.yml` → `design.lintcrux`),
   lints the full staged source set, and writes the SARIF — no
   hand-editing of anything.
2. GUI: `File → Import FuseSoC EDAM…` opens a picker filtered to
   `.yml`/`.yaml`; the imported project opens in a NEW TAB (same seam
   as File → Open) and the violations table populates.
3. The SERV `serv` (tool-API) capture: `-Wall` arrives as Verilator
   `warnFlags: [all]`, the `verilator_waiver.vlt` is passed to
   Verilator **before** the sources and to no other engine.
4. The SERV `servant` (flow-API) capture: the whole
   `serv → servile → servant` closure imports (26 sources, three
   cores), `toplevel: servant`, and `sourceFileProvenance` records
   which core contributed each file.
5. Reader warnings (unknown file types, other tools' options, version
   drift from 0.2.1) appear on stderr as `lintcrux: warning: …` and do
   not fail the run.

### 22.4 Edge cases

- An EDAM with `version:` ≠ `0.2.1` imports best-effort with a loud
  warning — the format is undocumented, and a hard gate would break on
  harmless point bumps.
- Declaration-only parameters (no `default`) apply **nothing** — a
  `vlogdefine` like SERV's `RISCV_FORMAL` must not become a define, or
  the design under lint changes.
- A `vlogparam` with a default becomes a Verilator-only `-G` option
  with a warning naming the asymmetry.
- Zero lintable HDL sources (e.g. a synthesis-only EDAM) → exit `65`
  with a clear message, never a silent empty project.

### 22.5 Tier-gate scenarios

Open Core — no gating. The importer, the CLI flag, and the menu entry
ship free; this is a distribution surface, not a monetization one.

## 23. Screen-reader and keyboard access

### 23.1 What it does (plain language)

What a screen reader announces as keyboard focus moves, and how far the
keyboard alone gets a user. The workspace screen, the imported-report viewer
and the web viewer are each divided into keyboard regions — toolbar or app
bar, the four IDE panes, the status bar, and on the workspace screen the
start canvas — and **F6** / **Shift+F6** jump between them; with focus in a
side or bottom pane, **Ctrl+Shift+Arrow** (**Cmd+Shift+Arrow** on macOS)
resizes it. At launch focus lands on the start canvas's **Open Project…**
button, so a screen reader has something to say. Focus that falls out of
the screen (a native file dialog closing, the start canvas replaced by a
tab) is put back inside it on desktop.

The violation table's rows are one Tab stop. **Up**, **Down**, **Home** and
**End** move between them; the focused row scrolls into view, draws a focus
ring, and is selected, so the Details pane follows it exactly as it follows
a click. **Enter** opens the violation in the editor (the double-click
action), **Space** toggles its check box, and **Shift+F10** or the Menu key
opens the row's context menu. Each row is announced as one sentence —
severity, rule, file, line and message — plus its check box state, and the
list speaks its keyboard hint when focus enters it. The rule browser's list
is one Tab stop too; **Up** / **Down** move between rules and the focused
rule's documentation link is the next Tab stop. The filter-preset dropdown
is announced by name and value, severity chips by one word, column headers
as buttons, a tab by its name with its path as the description, and each
tab's close button as "Close *name*". No user-visible string contains an
arrow glyph (a speech engine reads one as "question mark"); menu paths are
written `Settings > Engines`.

### 23.2 Setup

A release build. NVDA on Windows, or VoiceOver on macOS (Cmd+F5). Any SARIF
report; one with many violations across several engines exercises the most.

### 23.3 Step-by-step expected behavior

1. Launch with no tabs restored. Without touching the mouse, the screen
   reader announces the **Open Project…** button inside the welcome region.
2. Press Tab through the start screen: every stop is announced with a name,
   and Tab returns to Open Project… after the toolbar.
3. Press F6 repeatedly: focus moves between the toolbar and the start canvas
   (and the status bar when it holds a control).
4. Import the SARIF report (toolbar or start canvas). In the viewer, press
   Tab from **Import another…**: the rule browser costs one stop for the
   list (plus its documentation link), not one per rule.
5. With focus on a rule, press Down and Up: the next and previous rules are
   announced. Tab away and Shift+Tab back: focus returns to the rule last
   visited.
6. Continue to the violations: the list's keyboard hint is spoken, then the
   row as "*severity* violation, rule *rule*, file *file* line *line*:
   *message*" followed by "check box not checked". One Tab stop covers every
   row: the next Tab goes to the Details pane, which already shows the
   focused violation.
7. Back on the rows, press Down, Up, Home and End: each announces its row and
   the Details pane follows. Space checks the row; Enter opens the file at
   the violation's line in the configured editor; Shift+F10 opens the
   context menu when the build has entries for it.
8. Press F6 from anywhere in the viewer: focus jumps region to region
   without tabbing through the rules or rows in between. With focus in the
   rule browser, Ctrl+Shift+Right widens it.

### 23.4 Edge cases

- Filtering the rule browser (search or engine chip) so the rule holding the
  Tab stop disappears moves the stop to the first listed rule.
- Scrolling the rule list with the mouse until the Tab-stop row is far out
  of view drops the list from the Tab order until it is scrolled back —
  the row is not built. F6 still reaches the pane. The violation table
  handles the same case: the built row nearest the stop takes it.
- A click on a violation row moves the table's Tab stop there, so Tab from
  the filters returns to the row last clicked.
- Re-sorting or filtering keeps the Tab stop on the same violation while it
  is listed.
- The live-region limits of the desktop screen-reader engines apply: "not
  selected" on check boxes is an engine artefact, not a LintCrux defect.

### 23.5 Tier-gate scenarios

Open Core — no gating, identical under both `kBetaPeriod` values.
