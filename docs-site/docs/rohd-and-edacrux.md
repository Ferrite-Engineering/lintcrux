# ROHD + EDACrux, from LintCrux 1.2

[ROHD](https://github.com/intel/rohd) is Intel's open-source hardware framework written in Dart. You describe hardware as Dart classes, simulate it in Dart, and generate SystemVerilog or a netlist from the same code. This page is for ROHD users. It shows how to lint the SystemVerilog that ROHD generates, and how to see each finding at the Dart line that produced it, not only at a generated line you never edit.

!!! note "From LintCrux 1.2"

    Linting ROHD's SystemVerilog works in any LintCrux, because it is ordinary SystemVerilog. Showing the **Dart source** of a finding is from LintCrux 1.2 and needs ROHD 0.7 or later, with source tracing on (below). The other EDACrux apps have the same kind of page: [NetCrux](https://docs.netcrux.app/rohd-and-edacrux), [WaveCrux](https://docs.wavecrux.app/rohd-and-edacrux) and [SimCrux](https://docs.simcrux.app/rohd-and-edacrux).

## What LintCrux does with ROHD output

| You have | LintCrux | Where |
|---|---|---|
| SystemVerilog generated by ROHD | Lints it with the same engines as any SystemVerilog. | [Generate the SystemVerilog](#generate), [Lint it](#lint) |
| ROHD's source-trace file, `<Top>.flc.json`, beside the `.sv` file | Shows the Dart file, line and column next to each finding on a generated line, and **Go to Dart source** opens it in your editor. | [See the Dart line](#see) |
| The `// ROHD:` comments in the generated SystemVerilog, and no trace file | Uses the comments for the Dart location where they cover the line. | [See the Dart line](#see) |
| A finding you want to look at in the schematic or the waveform | Sends its location to NetCrux or WaveCrux over CXP. | [Cross-probe](#cross-probe) |

## Generate the SystemVerilog and the trace file {#generate}

Activate the source tracer before the design is built. Write the SystemVerilog, and then the trace file beside it:

```dart
import 'dart:io';
import 'package:rohd/rohd.dart';

Future<void> main() async {
  SourceTracer.activate();                  // ROHD 0.7 or later; before the design is built
  final top = MyDesign(Logic(), Logic());   // your top module
  await top.build();

  Directory('build').createSync(recursive: true);
  final sv = SystemVerilogService(top);
  File('build/MyDesign.sv').writeAsStringSync(sv.output);
  TraceService(
    top,
    svService: sv,
    packageRoot: Directory.current.path,
  ).write('build');                         // writes build/MyDesign.flc.json
}
```

`MyDesign.flc.json` is the source-trace file ("FLC": file, line, column). LintCrux reads version 6. It applies a trace file to the SystemVerilog file the trace file says it was written for, so keep the two names in step, as above. Generated SystemVerilog also carries `// ROHD:` comments when tracing is on, which LintCrux uses when there is no trace file.

## Lint it {#lint}

From the command line, with the headless `lintcrux`:

```bash
lintcrux build/MyDesign.sv --top MyDesign --sarif build/lint.sarif
```

Or write a project file once, `my_design.lintcrux`, and open it in the desktop app with `File → Open Project…`:

```json
{
  "version": 1,
  "name": "my_design",
  "rootPath": ".",
  "language": "systemverilog",
  "sourceFiles": ["build/MyDesign.sv"],
  "topModule": "MyDesign"
}
```

`lintcrux my_design.lintcrux --exit-code` fails a CI job on any finding. See [Exports & CI](exports-and-ci.md) and the [project file format](reference/project-file.md). A project can also be named in a `<design>.crux-project` file together with the design's other files: see [one file for the whole design](https://docs.netcrux.app/rohd-and-edacrux#manifest).

Your engines (Verilator, Verible and the others) run on the generated SystemVerilog as they would on handwritten SystemVerilog. A project's `severityOverrides` can lower a rule that you do not want applied to generated code. See [Projects & engines](projects-and-engines.md).

## See the Dart line {#see}

Select a finding on a generated line. Under the SystemVerilog location, the inspector shows **Dart source (ROHD 0.7 or later)**: the Dart file, line and column, a note on how LintCrux found it, and the callers. **Go to Dart source** opens it in your editor.

- **Exact.** The line declares, drives or connects a signal or an instance that ROHD recorded. The location is the Dart line that created it, and for an instance the callers include where it was instantiated.
- **Enclosing block or instance.** A line that only reads a signal, such as `if(valid_bit)`, has no record of its own. LintCrux follows the block or statement around it and shows the Dart line that created that.
- **From the `// ROHD:` comment.** Used when no trace file is found.

The finding's location stays the SystemVerilog line, so baselines and waivers are not affected. The Dart location is also written into exported SARIF, under `lintcrux.rohdSource` in the result's `properties`.

If the trace file is not next to the `.sv` file, name it in the project file:

```json
"perEngineOptions": {
  "rohd": { "sidecar": ["build", "other/Alu.flc.json"] }
}
```

Each entry is a file or a folder, relative to the project root. [SystemVerilog generated by ROHD](rohd.md) has the rules and the limits.

## Cross-probe with the other apps {#cross-probe}

LintCrux, NetCrux, WaveCrux and SimCrux find each other on the same machine and talk over **CXP**, the cross-probe protocol. Right-click a finding and choose **Cross-probe to** to send its location to a running app. See [Cross-probe](integrations.md#cxp).

### From your own Dart code, coming with EDACrux 1.2

A Dart package, `edacrux_cxp`, is coming with EDACrux 1.2. It is a pure-Dart CXP client with no Flutter dependency, so a running ROHD simulation or test can ask WaveCrux to show a signal and NetCrux to highlight a net. It is not published yet, so there is nothing to add to your `pubspec.yaml` today.
